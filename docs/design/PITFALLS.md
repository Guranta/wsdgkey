# 设计侧踩坑与决策记录（万事大吉 v2.1）

> 每条都写三件事：**决定**、**原因**、**走过的弯路**。来源是 `DESIGN.md` §0 变更记录、§13 待确认 / 已定事项，以及 2026-10-19 的需求沟通和线上走查。
> 时间均为北京时间（Asia/Shanghai）。以后迭代时，**改规则前先看这里**，免得把已经否掉的方案又捡回来。

---

## 1. 默认语言

- **决定**：优先级为 ① 用户手动选择 → ② 浏览器语言是 `en*` 就用英文 → ③ 其他一律中文。手动选择存在 cookie `shq-lang`（服务端渲染 `<html lang>` 需要），同时同步到 localStorage `shq-lang`。`<html lang>` 用 `zh-CN` / `en-US`。
- **原因**：用户主要是中文用户。只有明确是英文浏览器才切英文；日文、韩文等其他语言的浏览器也显示中文，比显示英文更合适。
- **弯路**（前后改了三次）：
  1. 最早定的是「默认 zh-CN」，完全不看浏览器。
  2. 后来改成「`zh*` → 中文，`en*` → 英文，其他 → 中文」，原型里一度还实现成了「`zh*` → 中文，其他 → 英文」，结果日文浏览器会显示英文。
  3. 最终定为上面这条。只有 localStorage 不够：服务端预渲染时读不到，导致 `<html lang>` 一直是 zh-CN，所以必须以 cookie 为准，再同步到 localStorage。
- **注意**：`/api/locale` 要能接受 `zh`、`zh-CN`、`zh-Hans`、`en`、`en-US` 等写法并统一处理，不支持的值要给出明确的错误。

## 2. 只保留浅色主题

- **决定**：只有浅色主题，深色模式、主题切换和深色 token 全部删除。原来放主题切换的位置换成「中 | EN」。
- **原因**：老板拍板；维护两套主题成本高，而且深色从来没进过验收范围。
- **弯路**：v2.0 曾留了一个「深色仅预览」开关和深色 token 附录，结果实现方跟着做了一半，表格、pill 的深色适配都要额外维护，最后整体删掉。

## 3. 批量测试移除，改为单条测试 + 10 分钟冷却

- **决定**：批量条只有「批量启用 / 批量禁用」。单行「▶ 测试」保留，同一渠道 **冷却 10 分钟**；**保存后、启用后各自动测试 1 次**（不受冷却限制，但会重置冷却）。
- **原因**：每次测试都会真实消耗上游额度，还会写一条测试日志（见第 6 条）。批量测试容易被误点或滥用，还会挤占拉取限流。
- **弯路**：
  1. 最初按 KeyMan 的做法，列表上**没有**测试按钮，测试模型只放在抽屉里。
  2. 后来老板要求「添加 / 测试 / 禁用 / 启用」四个动作都可见，于是加了行内测试和批量测试（带进度条和结果汇总）。
  3. 最后批量测试整体删除（进度条、结果、演示按钮都删了），只留单条测试加冷却。
- 批量启用后，每个渠道仍会自动测 1 次，结果并入批量结果弹窗的「其中又被自动禁用 n」。

## 4. 账单时间：从 12:00 改为 00:00 开始、拉完即发布、最晚 06:00

- **决定**：00:00 开始拉取前一日数据 → 失败渠道**立即重试 1 次** → 全部拉完（成功或未同步）**立即发布**，**最晚 06:00** → 未同步渠道不阻塞发布，之后自动补入，头部显示「已更新 n 个渠道」。
  - 拉取中：「账期 YYYY-MM-DD · 汇总中 n/总数 · 预计 x 分钟 · 最晚 06:00 发布」
  - 已发布：「已发布 YYYY-MM-DD 0x:xx」
- **原因**：凌晨就能看到账；拉取要按限流排队、可能耗时几十分钟，所以不能定死一个发布时刻，而是拉完就发。
- **弯路**：
  1. 先定了「每日 12:00 快照」。
  2. 改成「00:00 开始，失败重试到 11:30，12:00 发布」。
  3. 又加了「最晚 06:00」，和 12:00 互相矛盾。
  4. 最终删掉所有 12:00 和 11:30，改为现在这条。设计稿里残留的 12:00 / 11:30 文案用 rg 清过一遍，变更记录里只留了一行「已废弃」。
- **相关**：如果未同步渠道到**次日 00:00 之后**才补到，就无法再拆出单日数据，D 和 D+1 合并成一行，紫色「两日合计」，不拆分。

## 5. 基准值 = 累计 − 今日（先从日志数里扣掉模型测试）

- **决定**：
  - 每个渠道拉取时计算 `基准 = 累计 − 今日`，也就是当天 00:00 时的累计值，与什么时候拉到无关。
  - 前一日消耗 = 今日基准 − 昨日基准。重跑结果不变（幂等）。
  - **按 New API v1.0.0-rc.45 源码核实**：成功的渠道测试会写一条 type=2 的消费日志（`Model test` / `模型测试`），但**不改变渠道的 `used_quota`**。所以从日志统计（`/api/log/stat`）取数时，**先扣掉模型测试日志**，再参与基准计算和对账；被扣掉的部分单独记为「测试消耗」。
- **原因**：上游只给「今日」和「累计」两个数，而且「今日」在 00:00 清零，拉取又要持续好几个小时，所以只能反推 00:00 时的值。测试日志只出现在日志统计里、不进 `used_quota`，不扣掉的话两边口径就对不上。
- **争论（码农 vs keyman）**：keyman 担心「先从日志里扣测试，再把测试消耗单独列一行」会**重复计算**，或者在对账时制造出假差额。结论：
  - 测试本来就不进 `used_quota`，所以我方（基准差）里**没有**测试；日志侧扣掉之后，两边口径一致。
  - 测试消耗只在账单里单独列一行（不进 donut、不进供应商小计和合计），**只算一次，不重复**。
  - 这条依赖网关版本的行为。**升级 New API 后必须重新验证**「测试是否写日志、是否改 `used_quota`」（见第 15 条）。
- **弯路**：曾经给「没有昨日基准」的老渠道设计过「首次接入」，当天按网关日志统计，后来删掉了（见第 8 条）。

## 6. 测试消耗单独列示，不计入供应商

- **决定**：账单明细末尾单独一行灰色「测试消耗 · 渠道测试产生，不计入供应商合计」，后面才是「合计」。它**不进**供应商小计 / 合计，也**不进** donut；总消耗 donut 的图例另外注明「测试消耗 $x 单独列示，不计入」。
- **原因**：测试是平台或管理员发起的操作，不是供应商的用量，不能算到供应商头上。
- **弯路**：线上第一版把测试消耗做成了明细表里的一**列**，每个渠道一格，供应商看到后以为被扣了钱。走查后改成末尾单独一行。

## 7. 未同步不计为 0

- **决定**：从未成功拉到数据的渠道显示「—」加灰色「未同步」pill，**不计为 0**，不进小计、合计和 donut，图例注明「另有 n 个渠道未同步，未计入」。对账里归为「未同步」（灰 `#C7C7CC`）。
- **原因**：显示成 0 会让人以为这个渠道当天没用量，对账时也会被当成「一致」或者「启用但为 0」的异常，掩盖真正的问题。
- **注意**：上游返回 0 和查询超时要区分开：超时属于未同步 / 日志缺失，返回 0 才是真的 0。

## 8. 删除「首次接入」

- **决定**：删除「首次接入」标记和对应逻辑。保留绿色「新建」（前一日新建的渠道）。
- **原因**：账单和对账**只统计通过上号器添加的渠道**，每个渠道**在创建时就记下基准值**，所以不存在「没有基准的老渠道」。
- **弯路**：曾为「老渠道首次出现、没有基准」设计过蓝色「首次接入」pill（当天按网关日志统计，次日起按基准计算），设计稿和示例数据都做了，后来全部删掉。

## 9. 重新绑定规则

- **决定**（已与码农确认）：
  - **只有管理员能操作**；供应商视图不显示按钮，操作列显示「请联系管理员重新绑定」。
  - 场景：本地记录的 New API 渠道 ID 在网关上已经不存在（比如在 New API 后台删掉后重建了）。这类渠道在对账页出现在「网关上找不到」清单里，在渠道列表里显示红色「网关上已删除」。
  - 弹窗：输入「New API 渠道 ID」→ 点「校验」→ 成功时显示 **名称 / 类型 / 当前累计**，并提示「绑定后以此刻累计为起点，绑定前的消耗不计入」→ 只有校验成功后「确认绑定」才可点。
  - 如果这个 ID **已经被另一条记录占用**：结果置灰，显示「已被 #xxxx（创建人）占用」，**禁止确认**。同一个 New API ID 同一时间只能绑定一条本地记录。
  - 新 ID 以绑定时刻的累计为基准。绑定前的账单和对账记录**留在原记录、归原供应商**。旧 ID 删除到重新绑定之间的空档，按网关日志补齐；日志缺失就显示未同步。
  - 当天的账单明细行加紫色「已重新绑定 #73→#118」（英文「Rebound #73→#118」），渠道抽屉里有只读的「绑定历史」。
  - **每一次绑定和解绑都写入操作日志**（操作人、时间、本地渠道、旧 ID、新 ID、绑定时累计）。
- **原因**：账单是跟着本地记录和供应商走的，不能因为网关上换了 ID 就把历史账单搬走，或者丢掉。
- **弯路**：第一版弹窗在 ID 被占用时只给一个橙色提示「确认后将改绑」，允许抢占，存在把别人渠道绑走的风险。确认后改成禁止。

## 10. 密钥格式检查只警告、不拦截

- **决定**：`sk-` 前缀、段数、结尾 `/v1`、JSON 格式这类检查，有问题时只给**黄色**提示「格式可能不对，仍可保存」，**永远不禁用保存**。只有**真正的必填项缺失**（名称为空、新建时密钥为空、模型为空）才拦截。
- **原因**：New API 支持 50 多种类型，各家密钥格式五花八门，还经常变。前端误判一次就会把合法密钥挡在外面，用户只能找开发。
- **弯路**：第一版用红色错误并禁用了保存按钮，结果把合法密钥挡掉了，随后改成黄色警告。

## 11. 账单、对账、渠道列表只显示通过上号器添加的渠道

- **决定**：账单、对账、渠道列表**只显示通过上号器添加的渠道**；网关上别人直接建的渠道不显示。管理员看全部（通过上号器添加的），供应商只看自己的。账单和对账页头部有一行灰字「仅统计通过上号器添加的渠道」。
- **原因**：一个网关可能和别人共用，网关总量里含有别人的渠道。
- **弯路**：每日核对最初有一个「网关合计」行，拿网关日志总量和我方合计比，结果永远对不上（多出来的是别人的渠道）。后来删掉了网关合计核对，网关和分组只作为分组标题，**只按渠道逐个核对**。

## 12. 添加渠道表单与 New API 原表单完全一致（4 个 Tab、52 种类型）

- **决定**：添加 / 编辑抽屉的**字段、顺序、分组、默认值、类型列表和按类型显示的字段**，都和 New API 原表单（`channel-mutate-drawer.tsx` 等）一致，只换视觉。共 **4 个 Tab**（连接与模型 / 路由与映射 / 请求与响应 / 其他设置）、**52 种类型**（以 v1.0.0-rc.45 为准）。英文文案也沿用 New API 自己的英文。`DESIGN.md` §9.1.1 列出了每个字段对应的 New API 字段名。设计和源码冲突时**以源码为准**。
- **原因**：用户在 New API 后台和上号器之间来回切换，字段不一致就会填错；自己发明字段，后端也接不住。
- **弯路**：
  1. 最初按 KeyMan 设计：类型约 31 种，自己分「基础 / 高级」或「基本 / 密钥 / 高级」三段，不要权重，没有模型字段。
  2. 后来改成和原表单完全一致：加回模型（做成标签输入）、优先级、权重、标签、状态码映射等。
- **已知坑**：
  - 启用 / 禁用要用 `POST /api/channel/:id/status`，在 update 里直接带 `status` 会返回 "Invalid parameters"。
  - 火山方舟默认只给两个端点，要连点标签 10 次才解锁编辑。
  - Codex 凭证刷新走 `POST /api/channel/:id/codex/refresh`。
  - 抽屉底栏：取消 · 测试连接（原表单没有，按老板要求加的）· 黑色「创建渠道 / 更新渠道」（不叫「保存」）。

## 13. 线上走查发现的 27 处视觉差异（2026-10-19，`live-review/`）

对照 v2.1 走查线上供应商视图，一共 27 处。P0 和 P1 如下，P2 是视觉细节，摘要放在最后。

**P0**

1. 供应商访问 `/settings` 会被 307 跳回 `/channels`，可导航里又显示了「设置」。改为允许访问，只显示「我的账号」和只读的「账单时间」。
2. 账单缺少总消耗大 donut（外径 240、环宽 28、按类型分扇区、中心显示合计，放在第一行左上）。

**P1**

3. 供应商不应看到「按供应商」donut 和明细里的「供应商」列。
4. 剩余额度要做成 168px donut：黑色表示已用、绿色表示剩余，中心显示金额和「剩余 xx%」。
5. 账单明细按分组小计，列为「分组·渠道 / 今日 / 今日之前 / 累计」；测试消耗单独一行，删掉测试消耗列。
6. 对账颜色：未同步用灰 `#C7C7CC`，日志缺失用棕 `#A2845E`；每日核对用「待处理」，「待确认」只在供应商对账里用。
7. 供应商对账工具栏（月度 / 周度、账期、下载模板、上传 CSV、手动录入、导出 CSV）没数据时也要显示；供应商没有「锁定账期」。
8. 供应商渠道页副标题应为「仅显示你通过上号器添加的渠道 · …」。
9. 页面 h1 应为 26px/700、行高 1.25。
10. 主按钮被基础样式覆盖成了 16/400，应为 14–15/600（CSS 层级顺序问题）。
11. 供应商访问 `/users` 显示 404，应为 403「无权限访问该页面」。
12. 渠道空状态：3 个 blob、加粗主文案、灰色副文案「请联系管理员在 设置 › 网关 添加网关」；禁用状态的「添加渠道」要有说明原因的提示。
13. 抽屉底栏：新建时为「取消 · 测试连接 · 创建渠道」，编辑时为「更新渠道」。

**P2 摘要**：

- 抽屉：遮罩不透明度 0.35，焦点限制在抽屉内，`role=dialog`。
- 类型色用 teal `#30B0C7`，不是 `#5AC8FA`；类型头像用圆角方块，不用圆形。
- 卡片圆角 16；筛选控件 `#F3F3F3`、无边框、高 36。
- 表头 13/600。
- Tab 和「中 | EN」的选中态为白底加阴影，不是黑底。
- 分页为「共 n 条」、32px 页码、「20 条/页」。
- KPI 显示 $0.00 而不是 0。
- 账单 / 对账头部文案和 pill；空 donut 显示「暂无数据」；金额两种语言都用 `$`。
- 语言选择以 cookie 为主，同步到 localStorage。
- 加 `/reconcile` 路由别名。

**教训**：实现方的基础样式（Tailwind base / reset）容易把组件字号字重覆盖掉，走查时要专门看按钮和标题；供应商视图要单独走一遍，不能只看管理员。

## 14. 品牌：万事大吉

- **决定**：品牌名为「**万事大吉**」，中英文一致、**不翻译**、不加英文名。侧栏、顶栏、登录卡、设置页站点名称默认值、`document.title`、版本标签都已替换。「上号器」只作为功能名留在说明文字里。品牌标是黑色 blob 加两只白色竖椭圆眼睛，加一个青色高光；登录页用 96px 的 bot 脸，带克制的动画，系统开启「减少动态效果」时变成静态。
- **必须做**：`logo.svg` 的字标是 `<text>`，**交付前要转成轮廓**，否则在没有对应字体的系统上会走样。
- **不出现参考品牌**：设计早期参考过一个聊天机器人应用的视觉，现在设计稿、原型、SVG、截图、文档里**不能出现它的名字**。顶栏「视觉 · …」标签已删除。用 `rg -i` 检查，必须无结果。参考截图（`ref-*`）**不进仓库**。
- **弯路**：
  1. 英文品牌名先后叫过「Key desk」和「Key Manager」。
  2. 最后定为不翻译的「万事大吉」。英文界面里提到产品时也写「万事大吉」。
- 字标用 700，中文字距 +0.04em，不要沿用英文的负字距。

## 15. 固定测试网关的镜像版本

- **决定**：测试 / 验收用的 New API 网关**必须固定镜像版本**（当前核实的是 **v1.0.0-rc.45**），不要用 `latest`。升级前先看 changelog，升级后要重新验证下面这些依赖版本的行为，再改设计和实现。
- **原因**：下面这些都是从这个版本的源码核实出来的，换版本随时可能变：
  - 渠道测试写不写消费日志、改不改 `used_quota`（会直接影响第 5 条的基准算法和测试消耗）
  - 启用 / 禁用接口
  - 类型数量（52）和 Tab 结构
  - 按类型显示的字段（火山方舟、Codex 等）
  - `quota / 500000 = USD` 的换算（`QuotaPerUnit` 可配置）
- **弯路**：早期按 KeyMan 写的「约 31 种类型」，和实际源码对不上；表单字段也是按别人的截图猜的。

## 16. 不要把真实 token 写进设计文件或群聊

- **决定**：设计稿、原型、截图、文档、群聊里**只用打码的假 token**（`sk-••••末4位`），域名一律用 `*.example.com`，金额和用户名也都是虚构的。网关管理令牌保存后**只显示末 4 位**，也不会再返回明文。
- **原因**：设计文件会进 GitHub、会被转发；群聊有截图和历史记录；token 一旦泄露就能直接操作网关上的所有渠道。
- **检查方法**：提交前在 `docs/design/` 下运行 `rg -i 'gr[o]k|sk-pr[o]j|sk-[A-Za-z0-9]{20,}'`，必须无结果（模式里写成 `[o]` 是为了不让本文件自己被匹配到）。
- 如果真 token 已经发到群里或者提交过，要**立即作废并重新生成**，光删消息或者改提交历史不够。
