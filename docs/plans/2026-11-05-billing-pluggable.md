# 可插拔计费源计划

日期：2026-11-05。状态：计划。本文件不改应用代码。

配套：[供应商 JWT 网关](2026-11-05-supplier-jwt-gateway.md)、[验收用例](2026-11-05-billing-acceptance.md)（含 TBD 共 53 条，必过 50 条）。

决定已经做出：账单按网关种类选择计费源，不为本站写一套一次性特例。源 C 的汇率只用 `customer_billing.exchange_rate`。

## 1. 背景

现在的日账是一条算法，里面用 `gateway.kind` 分叉：

- `newapi_admin`：`used_quota − 今日日志` 得 0 点基线，日志先扣「Model test」和「模型测试」。日消耗是相邻基线差。对账再比渠道级 `/api/log/stat`。见 `lib/billing-math.ts` 的 `deriveBaseline`、`resolveConsumption`。
- `newapi_seller`：只在上海时间 0 点后 15 分钟内把列表里的 `used_quota` 记为快照，日消耗是相邻快照差，缺一侧就是未同步，不合并多日。见 `resolveSellerConsumption`、`pullSellerBaseline`。对账页改显示这份账单。

供应商 JWT 站上，抽样的 `used_quota` 全是 0，全站 `/api/log/stat` 与不带 channel 的日志不可用。渠道对象上的 `customer_billing` 才是金额：`source`、`state`、`currency`、`exchange_rate`、`amount_usd`，以及可选的 `as_of`、`stale`。`state=ready` 时有美元累计；`unavailable` 常见于 `dianju_bill_export`。2026-11-05 只读聚合大约 ready 383、unavailable 217，这是站点当时的分布，不是上号器已经跑出来的账。

渠道级 `GET /api/log/stat?type=2&channel=` 带 `start_timestamp` / `end_timestamp` **可用**。这修正了早先「日志完全不可用」的说法。它仍是辅助，不是日消耗权威。`/api/data` 的序列里见过 `channel_id: 0`，不能按渠道计费。站点钱包是普通用户钱包，余额为 0，不是供应商结算，不读。

## 2. 为什么是可插拔源

本站如果写成 `if (kind === "newapi_supplier")` 的特例，第三种算法会和 ainow 的快照差各维护一遍：缺数不能当 0、导入后才起算、时区、重试，都会改两次。下一次站点再换字段，还要再复制一份页面。

可插拔是：网关种类只选择源，源负责读出「某日 0 点的读数 + 质量」。日差、缺数、导入基线、导出列共用一套。界面用计费源标签区分，不为每个站点新开一页。

代价是迁移。今天 A/B 的数字来自 `channel_baselines` 和 `billing_rows.consumption`。把调用点收成接口时，最容易把旧账改掉。所以先用夹具锁住 `resolveConsumption` 和 `resolveSellerConsumption` 的输出，再换调用点。旧行不回写。新列空着就走旧渲染。

这个风险比「只给本站开特例」大，换来的是第四种源不用再碰对账页的主路径。决定仍是可插拔。

## 3. 三个源

| 源 | id | 网关 | 权威 | 日消耗 |
| --- | --- | --- | --- | --- |
| A | `quota_snapshot` | `newapi_seller` | `used_quota` | 相邻 0 点快照差。测试不从额度里扣（老板已确认测试不进 `used_quota`） |
| B | `log_stat` | `newapi_admin` | `/api/log/stat?type=2` | 现有基线公式。日志先扣测试令牌名。对账仍比渠道日志 |
| C | `customer_billing` | `newapi_supplier` | `customer_billing.amount_usd` | 相邻 ready 快照的美元差 |

种类到源的映射是固定的，不能在设置里把供应商 JWT 改成 A 或 B（SRC-01）。若实现上出现误配：A 读到的 `used_quota` 全是 0 时，拒绝出账并告警，禁止发布「全员 $0」。

`customer_billing.source`（例如 `dianju_call_logs`）是上游来源名，显示在行上，满足验收「标明点据金额」。它不替换 A/B/C 的 pill。pill 用设计文案：源 A「快照 · used_quota」，源 B「日志 · log/stat」，源 C「客户账单 · customer_billing」。

## 4. 质量与日差

读数先落质量，再谈金额。

| 质量 | 条件 | 金额格 | 进合计 / 环图 |
| --- | --- | --- | --- |
| `ok` | 两侧快照都在，`state=ready`，非 stale，金额可解析 | 美元，差为 0 时就是 `$0`（真零） | 进 |
| `missing` | 缺任一侧 0 点快照，或没有 `amount_usd` | 「缺数据」 | 不进 |
| `stale` | `stale=true` | 「—」，pill「过期」 | 不进 |
| `unavailable` | `state=unavailable`，或超时 / 5xx / 源挂了 | 「—」，pill「源不可用」 | 不进 |
| 未同步 | 这个渠道从未有过成功快照 | 「—」。若同时能打「缺数据」，优先「未同步」 | 不进 |

本计划对 BILL-C-04 选后一种：stale 当日不计入环，金额格不是 `$0`，也不把未采纳的读数当成今日消耗。tooltip 写「源标记 stale，不按 0 计」。原始读数可以出现在 tooltip，不能出现在金额格。

负差（BILL-C-07）：两侧都是 ready 且差为负时，不取绝对值，不当作 `$0`。打「异常」并告警，不进正常合计。TBD-01 确认累计口径之前，负差保持观察，不自动改成「冲正入账」。

缺昨日、今日有数（BILL-C-02 的相邻形态）：今日不能出日差。禁止把昨日当成 0，从而把累计全额记成今日。今日缺、昨日有：今日缺数据；同日补跑成功后才出日耗。

CSV：质量不是 `ok` 的行，金额列空着，另有质量列。不写 `0`（BILL-C-06）。

图例注明「另有 n 条未计入（缺数据 / 过期 / 源不可用 / 未同步）」。

## 5. 汇率

源 C 的折算只认该次快照上的 `customer_billing.exchange_rate`。设计文案里的 `customer_billing.rate` 就是这个字段。它经常是字符串 `"7.2"`，按数解析。

- 存和主列都是 USD（`amount_usd`）。主列沿用现有 `$` 格式。
- 有合法汇率时，环图和表头标明「汇率来源：customer_billing.exchange_rate」，并写出该次数值。CNY 只做次行 `≈ ¥…`，不替换主列。
- 缺汇率、解析失败：USD 日差仍可出（质量别的条件满足时），汇率位置写「汇率 —」。禁止用 1、7.2、status 页上的约 7.3 / 6.73，或钱包汇率去补。
- `quota_per_unit`（该站为 500000）只服务源 A/B 的额度换美元。它不是人民币汇率。
- 汇率变了不改写已经落库的 USD。每一天用自己那张快照上的汇率做 CNY 对照。

status 页上的另一套 USD rate 若要展示，只能作为只读元数据，并标明来源是 status，不能参与源 C 的金额。v1 可以不展示它们。

## 6. 快照任务

日界继续用 `lib/shanghai.ts` 的 Asia/Shanghai，不读容器本地时区，也不用浏览器时区切账期（BILL-C-10）。

源 C 一次列表走完，把本页每条已导入渠道的 `customer_billing` 记下来。禁止照搬 `pullSellerBaseline`：那个实现对每个渠道重扫列表，601 条会打成渠道数乘页数。也禁止 `lib/jobs.ts` 现在这种把所有缺基线渠道同时丢进 `pulling` 的扇出。

节奏：

1. 上海日 00:00 后开始。优先窗口是 00:00–00:15，希望读数靠近日界。
2. 单页失败按现有 `retryDelayMs` 退避，快重试最多 5 次。单页失败不影响其他页（SCALE-02 的精神：一批里一条失败不拖死整批；源 C 的「一批」是列表页，页大小 20，远小于 50）。
3. 快重试仍失败则降为每 15 分钟一轮，直到下一个上海日 00:00。同日补成功：该日从 `missing` 改为 `ok`，界面可打「补入 HH:mm」，并留审计「补快照」（BILL-C-11）。第一次成功之后，同日后来的读数不覆盖已成功的快照。
4. 越过下一个 00:00 仍没有成功读数：昨日保持缺数据。禁止把次日的值写进昨日，禁止前后日平均，禁止写 0（BILL-C-12、BILL-C-13）。源 C **不做**「两日合计」。源 A/B 保持今天的跨日合并行为，避免旧账变样。
5. 晚于 00:15 才第一次成功的快照仍然按验收算 `ok`，但要告警「快照晚于日界窗口」。在 TBD-01 若确认 `amount_usd` 是累计，这份晚快照会把日界之后的用量卷进差里，告警就是为了让这件事看得见。
6. 现有 06:00 发布可以照常发生。发布时还缺的行是缺数据，不是 0。同日稍后补成功再更新该行（沿用 `backfill_at` 的位置）。

`stale=true` 的读数不记为 `ok`，可在窗口内再试。到点仍 stale 则质量为 `stale`。

并发：该网关默认 2，与导入共用队列，避免快照和导入叠在一起把站打满。快照进行时，这个网关的常规列表轮询让路。上游没有给出限流头，所以上限以我们的队列为准（SCALE-04）。

告警：连续两个上海日快照失败；出现 `stale=true`；单日绝对差大于近 7 个 `ok` 日的中位数的 3 倍（`billing_spike_ratio`，默认 3，可改）。负差走第 4 节的异常告警。

## 7. 导入基线

与 ainow 已经约定的规则相同，源 C 用美元读数而不是 `used_quota`：

- 导入不改远程渠道（验收 CH-S-03）。
- 计费起点是导入之后的第一次 00:00 成功快照。这张是锚点（沿用 `import-anchor` 的含义），本身不是一日的消耗（BILL-C-20、BILL-C-21）。
- 锚点之前、以及还没到第一次 0 点的当天，显示「未到计费起点 / 待首次快照」，金额是「—」，不是 `$0`（BILL-C-22）。
- 不回填导入前的消耗。锚点日的下一张成功快照才产生第一笔日差。
- 不把 `used_quota=0` 写成 `source=create` 的基线。

导入默认已在网关计划定下：全部入库（当前 604 条，含 601 条仅可见）都进 `customer_billing` 快照；管理动作只对 `owned=true`。未导入的行不进快照。

三条探针（`xiaolou-01-wsdgkey-probe-should-fail`）现在是仅有的 `owned=true`，随全部导入进入可见和计费。站点管理员删除之后，可管集合可以为空，仅可见行的账单照常。

## 8. 源接口（草图）

实现时放在 `lib/billing-math.ts` 旁边的纯函数里，先有单测再接线。

```ts
type BillingQuality = "ok" | "missing" | "stale" | "unavailable";

type MidnightReading = {
  quality: BillingQuality;
  amount: number | null; // 仅 quality==="ok" 时有权威金额
  unit: "quota" | "usd";
  fxRate: number | null; // 源 C：customer_billing.exchange_rate；否则 null
  upstreamSource: string;
  pulledAt: number;
};

// 日差：两侧 quality 都是 ok 才返回数字。否则返回质量，金额为 null。
// 负差返回数字并带 anomaly，调用方不得取绝对值。
```

源的实现只负责把上游读成 `MidnightReading`。A 读额度快照，B 读现有基线公式，C 读 `customer_billing`。日差函数不关心 HTTP。

## 9. 表结构

不改旧行的含义。SQLite 与 Postgres 都用现有的补列方式。

新表 `billing_snapshots`：

| 列 | 说明 |
| --- | --- |
| `channel_id`, `day`, `source_id` | 主键。`day` 是上海日 |
| `quality` | 第 4 节 |
| `amount` | 权威读数；非 ok 为空 |
| `unit` | `quota` 或 `usd` |
| `fx_rate` | 源 C 的 `exchange_rate`；没有就空 |
| `upstream_source` | 如 `dianju_call_logs` |
| `state`, `stale`, `as_of` | 原样留下，便于解释 |
| `pulled_at` | 实际拉到的时间 |
| `note` | `import-anchor`、`backfill`、`late` 等 |

`channel_baselines` 继续给源 A/B 用，不把历史额度行搬进新表。

`billing_rows` 只加可空列：`billing_source`、`quality`、`amount_usd`、`fx_rate`、`upstream_source`。旧列 `consumption`、`kind`、`test_quota`、`log_quota` 保留。

读的时候：

- `billing_source` 为空：按今天的 `kind` + `consumption` 渲染，美元仍是额度 / 500000。这是升级后旧账还能打开的路径（SRC-04）。
- `billing_source=customer_billing` 且 `quality=ok`：主列用 `amount_usd` 的日差。
- 质量不是 `ok`：金额格按第 4 节，合计跳过。

不提供「把旧账重算进新表」的迁移。回填会改历史数字。

## 10. 对账

| 网关 | 源 | 对账页 |
| --- | --- | --- |
| `newapi_admin` | B | 保持渠道级我方 vs 日志，容差、测试扣减、缺日志判断都不变（REC-S-03、SRC-03） |
| `newapi_seller` | A | 保持现在的账单视图，不出现「全部一致」 |
| `newapi_supplier` | C | 对账入口直接是该网关的账单。没有一致/异常 donut，禁止「全部一致」或「不支持」（REC-S-01） |

源 C 可以多一列「日志辅助」：`GET /api/log/stat?type=2&channel=<导入的供应商列表 id>&start_timestamp&end_timestamp`。列头或 tooltip 写「辅助源，可能暂时不可用」，并写「仅辅助，不作为权威」。

- 辅助失败、全站不可用、或暂时 unavailable：这一列是「—」。账单仍按 `customer_billing` 的日差显示，不把账单打成缺数据或 `$0`（SRC-05、REC-S-02）。
- 辅助数字和日差不一致：不改日差，不标红成对账异常。
- 日志行里的 channel 可能是客户侧 id，和列表 id 的 `log/stat` 总量可以不同。辅助列只用导入时的列表 id，不把客户侧 id 加总后再去对权威金额。
- 有可用日志的网关（源 B）继续走渠道级对账，不要因为源 C 的存在改掉它们。

## 11. 下钻、导出、规模

层级是网关 → 渠道 → 模型。源 C 的 `customer_billing` 没有模型维，模型层不渲染空壳。源 B 在日志能拆模型时才有模型层。

导出是账单页上的「导出账单 CSV」，和现有对账导出分开。列至少含：账期、网关、渠道 ID、名称、计费源、质量、USD 金额（非 ok 为空）、汇率来源、rate、上游 source。供应商只导出自己的行。601 行走服务端生成，避免浏览器一次算完全表。环图和 KPI 用服务端聚合，前端不把全量渠道拉来求和（SCALE-03）。

列表和账单明细保持分页。导入进度见网关计划。

## 12. 和现有行为的对应

| 现有 | 可插拔之后 |
| --- | --- |
| 未同步 | 保留。从未成功拉取。与「缺数据」同时成立时显示「未同步」 |
| 两日合计 | 源 A/B 保留。源 C 不用，缺日只打「缺数据」 |
| 补入 HH:mm | 源 A/B 保留。源 C 同日补成功后可打，并去掉「缺数据」 |
| 新建 / 导入 | 本应用创建仍用「新建」。导入用灰「导入」。导入前的格子是「—」 |

| 测试消耗行 | 源 A/B 且该网关允许测试时保留。源 C 不显示。本站也不要为了验证去点线上测试 |
| 快照计费 | 升为源 A 的标签「快照 · used_quota」。「快照计费」留一个版本当别名 |

i18n：新字符串同时进 `messages/zh-CN.json` 和 `messages/en.json`。`npm test` 会因为缺键失败。

## 15. 已验证 / 未验证

对照日 2026-11-05。「已验证」只包括对供应商站的只读核对，以及本仓库里已经存在的行为。「未验证」是上号器还没做、不能当成已经上线。

### 1. 真零、缺数据、过期、源不可用

- 已验证：该站抽样 `used_quota` 恒为 0。拿它做日差会得到全员 `$0`。`customer_billing` 同时存在 `state=ready`（有 `amount_usd`）和 `state=unavailable`，并有 `stale` 字段。约数见第 1 节，不是 UI 验收。
- 未验证：账单 DOM 在缺数据 / 过期 / 源不可用时不含 `0`、`$0`、`$0.00`；真零只在质量 `ok` 且差为 0 时出现（BILL-C-01～06）。
- 计划：第 4 节。异常格不进合计和环图。

### 2. 汇率与币种

## 评审意见

### 设计

1. **假零**：任何质量异常格若渲染成 `$0`，供应商会当成真实零消耗。验收必须断言：缺数据/过期/源不可用/未同步的 DOM 文本不是 `0`/`$0`/`$0.00`。
2. **跨天**：快照时刻锁定北京时间 0:00；「两日合计」仅 A/B 补拉场景；C 缺日只「缺数据」。跨时区展示仍用账期日，避免用浏览器本地日切。
3. **导入当天**：导入日若尚无 0:00 快照，当日与此前均为「—」；次日 0:00 之后才出现第一笔差值。文案写进导入成功 toast / 弹窗注脚，避免客诉「导入后账单是 0」。
4. **汇率**：必须标 `customer_billing.rate` vs `status USD rate`；环图旁缺 rate 时显示「汇率 —」，禁止静默用默认 7.2。CNY 只作对照次行。
5. **601 渠道性能**：导入并发建议 2；列表分页；KPI/donut 用服务端聚合，前端不按全量渠道算环图。导出 CSV 走异步任务+下载链，避免浏览器卡死。
6. **对账假绿**：仅 C 的网关若仍画「一致」donut，会造成虚假安心——设计上直接切账单视图，评审时盯死。
7. **可插拔优于特例**：UI 用「计费源」标签驱动显示，避免再为每个站点写一套隐藏逻辑；新站点只需挂源，不新开页面。
